# 0004. Данные читаем на клиенте, сервер отвечает за вход

**Дата:** 2026-09-07
**Статус:** принято

## Контекст
Приложение целиком за логином, SEO не нужно. Next.js предлагает грузить данные
в Server Components — это быстрее и безопаснее. Но офлайн требует, чтобы экраны
открывались из локального кэша, а Server Component без сети не отрендерится.

## Решение
Граница проходит по офлайн-доступности:

- welcome и вход — Server Components;
- защита маршрутов и обновление сессии — `proxy.ts`;
- всё за логином — Client Components, данные через `sync` (кэш + сеть);
- экспорт и тяжёлые агрегаты — Route Handler на сервере.

## Почему
1. Экран, который должен открываться в самолёте, не может зависеть от рендера на сервере.
2. Два пути загрузки одних данных (серверный и клиентский) означали бы два кэша,
   которые разойдутся.
3. Права всё равно проверяются в базе через RLS, так что клиентское чтение не создаёт
   дыры в безопасности.

## Чем платим
Первый показ экрана медленнее, чем при серверном рендере: сначала оболочка, потом
данные. Нужны скелетоны. Часть логики уезжает в браузер, размер бандла растёт.

## Что рассматривали ещё
- **Всё на Server Components.** Быстрее и элегантнее, но несовместимо с офлайном.
- **Гибрид на каждом экране.** Сервер отдаёт первый экран, клиент обновляет. Звучит
  идеально, на практике даёт двойную загрузку и мигание данных.
